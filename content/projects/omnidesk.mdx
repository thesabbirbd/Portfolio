## The Problem

Building a generic e-commerce site is simple, but building one that supports complex, conditionally-dependent products (like a custom PC builder where choosing a specific CPU limits your choice of Motherboard) is a significant relational data challenge. Omnidesk BD needed a highly responsive interface combined with a strict backend rule engine to prevent users from placing invalid or physically incompatible orders.

## The Approach

The platform is split into a decoupled frontend (Next.js) and backend (Node.js/Express). The backend acts as the source of truth for product availability, pricing calculations, and compatibility validation.

### Architecture Evolution

Initially, the database handled all compatibility checks on every page load. As the product catalog grew, this became a bottleneck. 

I introduced **Redis** as a caching layer between the Node API and PostgreSQL. Now, standard product queries hit the cache, while complex build-validations hit the relational database.

## Engineering Decisions & Trade-offs

**Decision:** Separating the Admin Panel from the Main Storefront  
*Context:* Both systems needed to access the same database but had vastly different security and bundle-size requirements.  
*Trade-off:* We accepted the overhead of maintaining two separate frontend codebases in exchange for a drastically lighter customer-facing bundle and tightly locked-down admin security rules.

## What Didn't Work (Failures & Iterations)

During early testing, the custom PC builder form was entirely client-side. This seemed fast, but it allowed tech-savvy users to manipulate the DOM and bypass compatibility warnings before submitting the cart payload. 

*The Fix:* We had to rewrite the validation logic so that the backend re-validates the entire build graph at checkout, completely ignoring client-side compatibility flags.

## Current State & Future Direction

Omnidesk BD is currently active and processing live orders. The next engineering phase involves migrating the monolithic Node API into smaller, domain-specific microservices (e.g., separating the Order Service from the Product Catalog Service) using Docker to prepare for future horizontal scaling.
